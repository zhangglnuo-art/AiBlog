大模型生成答案需要逐 token 往后写。若等整段文本全部完成才返回，用户可能盯着空白页面十几秒；流式输出（Streaming）会把生成中的片段持续发送到前端，让用户先看到第一句话。

它不一定减少总生成时间，却能显著改善等待体验。

## 两个关键指标

**首 token 延迟**：用户从发送到看到第一个字等多久。它受网络、排队、输入长度和模型预填充影响。

**总完成时间**：完整答案生成完需要多久。它受输出长度、模型速度和工具调用影响。

流式输出主要改善前者；若答案本身很慢，仍要通过缩短上下文、模型路由和缓存来优化。

## 一个稳健的实现流程

1. 后端与模型 API 建立流式连接。
2. 将文本增量和工具事件转发给前端。
3. 前端按顺序追加内容，并区分“生成中”“工具处理中”“完成”“失败”。
4. 连接中断时保留已收到内容，允许重连或重新生成。
5. 最终完成后再写入完整消息和审计记录。

不要在每个 token 到达时都触发昂贵的数据库写入或整页重渲染；应适度批量更新。

## 流式输出的安全问题

完整答案生成后再审核很简单，但流式输出已经把内容展示给用户。需要设计适合流的安全策略：对高风险请求先做输入过滤，对工具动作保留审批，对检测到的问题能够停止后续输出。

对外发送、付款或修改数据等行为，更不能因为“流已经开始”就直接执行。文本流和动作流应该分开管理。

## 常见坑

- 网络断开导致用户看到半句，却不知道是否完成
- Markdown、代码块被分段时渲染闪烁
- 多轮生成并发导致内容串到错误会话
- 用户点停止后，后端仍持续消耗 token
- 只优化首字延迟，忽略工具调用和长上下文

## 总结

流式输出让 AI 的逐 token 生成过程变得可见，核心价值是更快的反馈感。实现时要同时处理顺序、断线、取消、渲染和安全边界；把“看见文字”与“允许执行动作”分离，体验和可靠性才能兼得。
